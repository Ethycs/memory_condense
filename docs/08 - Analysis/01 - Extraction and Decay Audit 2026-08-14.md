# Extraction and Decay Audit — what actually reaches the prompt

**Status:** CURRENT for Finding 1 — **Finding 2 reinterpreted 2026-08-15**, see the correction below. Measured against `f2be62d`
**Cost:** $0. No API key, no network, no LLM call. Local corpus + `RuleBasedExtractor` + `ContextPacker` only.
**Why it exists:** `06 - Roadmaps/00` gates design Phase 4 (cold-tier era summaries) on *"evidence that COLD items are worth keeping at all."* This audit went looking for that evidence and found the opposite of what the gate assumes.

## Summary

Two findings, both free, both decision-relevant, neither previously measured:

1. **The memory header is budget-bound, not decay-bound.** 70.6% of extracted memory items never reach the prompt — dropped by a fixed 900-token ceiling long before decay is consulted.
2. **COLD is unreachable by construction.** No evaluation run can currently produce a single COLD item, so the evidence Phase 4's gate asks for cannot be generated by the harness as it stands.

> ## Correction — 2026-08-15: Finding 2 is a symptom, and its prescribed fix was wrong
>
> **The measurement below is correct. Its diagnosis is not.** An item needing 7–11.75 days of no access to reach COLD is not a limitation of the *harness* — it is a proof that the **decay coordinate is wrong**. A tier the system can never reach through its own operation is not a tier.
>
> Decay was specified in wall-clock seconds ([`arch_instructions.md:75`](../../arch_instructions.md), unedited since commit `0871e05`). The design intent is **per-turn**: each subsequent turn differentially assigns decay, so the conversation itself decides what stays warm. Under seconds an ingest completes in minutes, so `elapsed ≈ 0` and *every* item holds a decay factor of ~1.0 — retrieved or not.
>
> This document got within one step of that. Line 59 correctly says *"either the gate changes, or something must change first to make COLD reachable."* It then prescribed the wrong change: **wiring decay into ranking and enforcing the HOT cap do not make COLD reachable.** They make energy *count* — but a near-constant energy counted at weight 0.2 still discriminates nothing. The prescription addressed a different defect than the one diagnosed.
>
> Consequences: the follow-on `--answer-recall` survival numbers (**4.8%** of answers held by a memory item, **0.0%** surviving to day 14) are **void**. The day-14 figure could not have been anything else — COLD begins below `0.25`, energy is clamped to `≤ 1.0`, and `0.25 = 1.0 × 0.5²`, so 14 days is exactly the theoretical ceiling for any unpinned item.
>
> **Finding 1 is unaffected** — the 900-token header ceiling drops items before decay is consulted regardless of what decay counts. If anything the re-coordination sharpens it: the ranking that ceiling truncates will now be discriminating.
>
> See [`06 - Roadmaps/01 - Delivering the Specified System.md`](../06%20-%20Roadmaps/01%20-%20Delivering%20the%20Specified%20System.md).

A third observation falls out of the first: the default extractor's output is dominated by false positives.

## Corpus

40 unique conversations, 4,554 turns, from the same local directory that produced every number in `00 - Retrieval Ablation Results`. (47 files load; 7 are duplicate exports of the same conversation and are collapsed by content.)

The corpus is not committed — it is personal transcripts outside the repo. What is reproducible is the method; see the verification block.

## Finding 1 — 70.6% of memory items never reach the prompt

Extract with the default `RuleBasedExtractor`, seed energy via `decay.seed_energy`, then pack with `ContextPacker._build_memory_header` at its default budget.

| Measure | Value |
| --- | --- |
| Memory items extracted | 4,463 |
| **Dropped by the 900-token header budget** | **3,151 (70.6%)** |
| Conversations exceeding the budget | 27 / 40 |
| Median per-conversation drop rate | 64.4% |
| Items seeded HOT | 3,914 (87.7%) |

Worst individual case — the 283-turn transcript behind run pair A: 217 items, **190 dropped (87.6%)**, 7,719 tokens of header competing for 900.

The mechanism is not subtle. [`ContextBudget.memory_header_tokens`](../../src/memory_condense/context_packer.py#L35) is a flat `900`, and [`_build_memory_header`](../../src/memory_condense/context_packer.py#L114-L141) walks the ranked list accumulating bullets until the budget is gone, counting the rest as `dropped`. **It never reads `energy` or `heat`.**

### Why this bears on Phase 4

Phase 4 compresses COLD items into era summaries so they can keep contributing. But those summaries land in *the same 900-token header that already cannot fit the HOT items*. On this corpus the binding constraint is header capacity and extraction precision — not cold storage.

That is not proof Phase 4 is worthless; a summary is denser than the items it replaces, so it could win header space on merit. It is proof that **"COLD items are being lost" is not the problem to solve first** — items are being lost while still warm, by a ceiling that decay never sees.

## Finding 2 — no evaluation run can produce a COLD item

`HOT ≥ 0.75`, `WARM ≥ 0.25`, half-life 7 days ([schemas.py:86-90](../../src/memory_condense/schemas.py#L86-L90)). Time of *no access* required to fall below WARM:

| Seeded at | Reaches COLD after |
| --- | --- |
| 0.5 (ordinary, importance < 0.7) | **7.00 days** |
| 0.8 (important) | **11.75 days** |

An eval run is minutes of wall clock. Three independent mechanisms then close the remaining doors:

1. **`retrieve` reheats what it returns** ([memory_store.py:367](../../src/memory_condense/memory_store.py#L367)), and `reheat` adds a flat `REHEAT_BOOST = 0.25`, so any item recalled even once sits at ≥ 0.25 — WARM by definition.
2. **No clock can be injected.** `MemoryStore.retrieve` and `heat_counts` both accept a `now` parameter, but the facade drops it: [`condenser.recall_memories`](../../src/memory_condense/condenser.py#L145-L153) and [`condenser.heat_counts`](../../src/memory_condense/condenser.py#L212-L214) call through without forwarding it.
3. **Dataset time is discarded.** LongMemEval ships `haystack_dates` and LoCoMo ships `session_N_date_time`; `loader.BenchmarkSample.turns` is `list[tuple[str, str]]` — role and text only. The timestamps are used for format sniffing and then thrown away.

**Therefore Phase 4's gate is unsatisfiable as written.** Not "hard to satisfy" — structurally impossible with the current code. Either the gate changes, or something must change first to make COLD reachable.

The plan of record takes the second route: wiring decay into ranking (it currently affects nothing but display — see below) and enforcing the design's HOT cap are what give `COLD` a meaning that a measurement can address.

## Finding 3 — the default extractor is mostly false positives

Type and source distribution across all 4,463 items:

| Type | Count | Share |
| --- | --- | --- |
| Constraint | 2,905 | 65.1% |
| Correction | 1,005 | 22.5% |
| Definition | 331 | 7.4% |
| Task | 214 | 4.8% |
| Preference | 4 | 0.1% |
| Decision | 4 | 0.1% |

| Source turn role | Count | Share |
| --- | --- | --- |
| assistant | 4,154 | **93.1%** |
| user | 309 | 6.9% |

Both distributions are wrong for a system whose purpose is remembering what the *user* established.

The cause is [`RULES`](../../src/memory_condense/extractor.py#L61-L108). The `Constraint` pattern matches `must|never|always|don't|cannot|can't|required to`. In technical prose that fires on ordinary modality — *"the map must be smooth"*, *"this cannot happen"* — which is exposition, not a durable user constraint. And because assistant turns are ~10–60× longer than user turns in this corpus, the assistant supplies almost all the sentences and therefore almost all the matches. `Decision` and `Preference` — the two types the system most wants — total **8 items out of 4,463**.

Every one of these carries valid verbatim provenance. Provenance guarantees a memory is traceable; it says nothing about whether it was worth recording.

This is the evidence `06 - Roadmaps/00` Tier 2 asks for before promoting `LLMExtractor` out of gated status: *"evidence that rule-based extraction is the bottleneck."* 65% spurious Constraints and 93% assistant-sourced is that evidence.

## What this does not show

- **Nothing about answer quality.** These are counts, not scores. A dropped item may have been useless; a spurious Constraint may never be retrieved. Whether any of it changes an answer requires the paid benchmark run.
- **Nothing about `LLMExtractor`'s output**, which has never been run against this corpus — it has no provider binding in the repo.
- **Nothing external.** Still no common-benchmark number, so still no competitiveness claim.

## Consequences recorded elsewhere

- `06 - Roadmaps/00` — Phase 4's gate marked unsatisfiable-as-written, with the dependency made explicit.
- `02 - Implementation/02` §6 — the auto-capture rationale table asserted that decay demotes unused items and that reheating only fires on genuine matches. Both describe `decay.py` accurately and *retrieval* inaccurately: `ranking.rank_score` has no energy or heat term, so nothing decay computes influences what is returned.
